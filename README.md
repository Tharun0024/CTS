# Prior Authorization Claim Ingestion & Simulation Pipeline

A Python-based pipeline for ingesting longitudinal clinical data, simulating Prior Authorization (PA) scenarios, processing manual clinical submissions, and generating normalized, decision-free claim payloads for downstream **RAG Retrievers** and **Decision Agents**.

The system is designed to support reproducible PA workflow simulations, multi-attempt claim submissions, evidence tracking, and downstream policy evaluation.

# ▶️ Running the Pipeline

## 1. Ingest Clinical Data

Initialize the SQLite database and bulk-load the Excel/CSV datasets.

```powershell
python pa_pipeline/pipeline_main.py ingest
```

This process:

* Initializes the database schema
* Enables database constraints
* Loads patient demographics
* Loads longitudinal clinical events
* Loads configured policy data
* Preserves foreign-key relationships

Run this command once when setting up or rebuilding the database.

---

## 2. Run a Simulation for a Specific Patient

Run a PA simulation for a specific patient:

```powershell
python pa_pipeline/pipeline_main.py run-simulation --patient-id PA045 --scenario-type EVIDENCE_OMITTED
```

### Available Scenario Types

| Scenario           | Description                                                               |
| ------------------ | ------------------------------------------------------------------------- |
| `COMPLETE`         | All required clinical evidence is available and submitted                 |
| `INCOMPLETE`       | Required clinical information is insufficient                             |
| `AMBIGUOUS`        | Clinical records contain conflicting information                          |
| `EVIDENCE_OMITTED` | Required evidence exists but is intentionally omitted from the submission |

---

## 3. Run a Seeded Simulation Sequence

Run simulations for multiple randomly selected patients:

```powershell
python pa_pipeline/pipeline_main.py run-simulation --limit 5 --interval-seconds 3 --seed 123
```

### Parameters

| Parameter            | Description                            |
| -------------------- | -------------------------------------- |
| `--limit`            | Number of patients to simulate         |
| `--interval-seconds` | Delay between simulations              |
| `--seed`             | Random seed for reproducible execution |

Using the same seed produces a reproducible patient-selection sequence.

---

## 4. Process a Manual Clinical PDF

Process a manually submitted clinical PDF:

```powershell
python pa_pipeline/pipeline_main.py process-manual --file Aetna_Knee_Arthroplasty_PA_Input.pdf
```

The parser extracts information such as:

* Patient demographics
* CPT procedure codes
* Diagnoses
* Conservative treatment history
* Clinical evidence

The extracted information is inserted into the database and corresponding output payloads are generated.

# 🧪 Scenario Simulation

The simulator generates clinical facts and evidence conditions. It **does not make authorization decisions**.

The downstream Decision Agent is responsible for evaluating the claim.

### `COMPLETE`

All required evidence is available and submitted.

Example:

```text
Clinical documentation
       ↓
Imaging evidence
       ↓
Conservative treatment
       ↓
12 weeks of physical therapy
       ↓
Complete submission
```

---

### `INCOMPLETE`

The patient's clinical records do not contain sufficient evidence.

Example:

```text
Clinical documentation
       ↓
Imaging evidence
       ↓
Only 1–2 weeks of PT
       ↓
Incomplete submission
```

---

### `AMBIGUOUS`

The clinical information contains conflicting or inconsistent evidence.

Examples include:

* Conflicting dates
* Conflicting diagnoses
* Inconsistent clinical documentation

---

### `EVIDENCE_OMITTED`

The patient's database contains complete clinical evidence, but selected evidence is intentionally excluded from the initial submission.

Example:

```text
Complete Patient Record
        │
        ├── Clinical Notes
        ├── Imaging
        └── 12 Weeks PT
                │
                ▼
        Attempt 1 Submission
        PT Evidence Omitted
                │
                ▼
        Downstream Agent
        Identifies Evidence Gap
```

This scenario is primarily used to model resubmission workflows.

# 🔄 Multi-Attempt Resubmission

The system maintains a **stable claim identifier** across multiple submission attempts.

Example:

```text
Patient: PA045
     │
     ▼
Claim: CLM-8BA436
     │
     ├── Attempt 1
     │      ├── EV-1
     │      └── EV-2
     │
     │      Missing PT evidence
     │
     └── Attempt 2
            ├── EV-1
            ├── EV-2
            └── EV-3
                  │
                  ▼
            PT evidence restored
```

### Resubmission Behavior

When a claim is resubmitted:

1. The original `claim_id` remains unchanged.
2. A new record is created in `claim_submissions`.
3. The submission receives a new attempt number.
4. New evidence can be appended to the submission.
5. The transformation layer retrieves the latest attempt.
6. A new canonical claim payload is generated.

For example:

```text
Attempt 1 → claim_id = CLM-8BA436
Attempt 2 → claim_id = CLM-8BA436
```

The stable claim identifier allows the complete lifecycle of a PA request to be tracked.

# 🔗 Downstream Integration

The pipeline generates two primary JSON payload types inside the `output/` directory.

```text
output/
│
├── canonical_claim_<id>.json
│
└── rag_input_<id>.json
```

These payloads contain **clinical and policy context only** and are designed to remain decision-free.

---

## A. Canonical Claim JSON

### Target

**Decision Agent**

### Example Structure

```json
{
  "claim_id": "CLM-8BA436",
  "patient_id": "PA045",
  "policy_id": "CPB-0660",
  "attempt": 1,
  "patient_demographics": {},
  "procedure": {},
  "diagnoses": [],
  "evidence_refs": []
}
```

### Key Fields

| Field                  | Description                                 |
| ---------------------- | ------------------------------------------- |
| `claim_id`             | Unique claim identifier                     |
| `patient_id`           | Unique patient identifier                   |
| `policy_id`            | Insurance policy identifier                 |
| `attempt`              | Current submission attempt                  |
| `patient_demographics` | Patient demographic information             |
| `procedure`            | Requested procedure and CPT information     |
| `diagnoses`            | Relevant diagnosis information              |
| `evidence_refs`        | Evidence submitted with the current attempt |

---

## B. RAG Input JSON

### Target

**RAG Retriever**

The RAG payload provides the information required to retrieve relevant sections from insurer policy documents.

### Example Structure

```json
{
  "claim_id": "CLM-8BA436",
  "patient_id": "PA045",
  "insurance": "Aetna",
  "policy_context": {},
  "clinical_facts": [],
  "policy_questions": []
}
```

### Key Fields

| Field              | Description                                             |
| ------------------ | ------------------------------------------------------- |
| `claim_id`         | Unique claim identifier                                 |
| `patient_id`       | Unique patient identifier                               |
| `insurance`        | Insurance carrier, such as Aetna or CMS                 |
| `policy_context`   | Policy ID and policy title                              |
| `clinical_facts`   | Relevant patient clinical facts                         |
| `policy_questions` | Questions used to retrieve relevant policy requirements |

# 📌 Important Design Principles

### Decision-Free Data Generation

This pipeline does **not** determine whether a claim should be approved or denied.

Its responsibility is to provide structured information to downstream systems.

```text
Pipeline
   ↓
Clinical + Policy Context
   ↓
Decision Agent
   ↓
Authorization Decision
```

### Stable Claim Identity

A claim maintains the same `claim_id` throughout its submission and resubmission lifecycle.

### Evidence Traceability

Evidence is referenced through identifiers so that each submission can be audited and compared across attempts.

### Reproducibility

Simulation runs can use a random seed to produce repeatable results.

### Separation of Responsibilities

The system separates:

* Data ingestion
* Clinical simulation
* PDF parsing
* Claim transformation
* RAG retrieval preparation
* Authorization decision-making

This makes the pipeline easier to test, maintain, and integrate with downstream AI agents.
